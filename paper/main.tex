\begin{abstract}
Question answering over tables and text requires both identifying evidence and
applying operations to that evidence. We describe Online-KG, a framework that
constructs a knowledge graph for each question and uses executable candidate
programs to produce answers. The design combines structural table triples with
semantic triples extracted from accompanying passages. Candidate reasoning
paths are translated into Python programs, executed through a restricted graph
interface, and evaluated using execution outcomes and recorded evidence access.
A typed numerical intermediate representation provides a complementary way to
express arithmetic operations and track their inputs. We formulate an evaluation
protocol on HybridQA and FinQA to examine answer quality, the contribution of
graph structure and execution, and computational cost. This working draft
describes the intended study; comparative benchmark results remain to be added.
\keywords{Knowledge graphs \and Retrieval-augmented generation \and Executable reasoning \and Table question answering}
\end{abstract}

\section{Introduction}
Tables encode relationships through row identity, column labels, and sometimes
hierarchical headers. Accompanying passages can supply additional entities,
events, or numeric operands. A question may require joining these sources before
performing a computation. Our research question is whether a graph constructed
at query time, coupled with executable reasoning and evidence-aware selection,
can improve answer quality under a controlled context setting.

The proposed study investigates three components: structural table-to-graph
construction, execution of multiple candidate reasoning paths, and selection
using evidence access and source support. These are candidate contributions,
whose empirical value and novelty require validation.

\section{Problem Formulation}
Given a question $q$, a table $T$, and associated passages $D$, the system
produces an answer $a$ and an execution trace. In the initial benchmark setting,
$T$ and the associated passage pool are provided by the dataset. Passage ranking
therefore operates within supplied context; this is not an evaluation of
open-domain retrieval. The graph $G_q$ is constructed separately for each query.

\section{Method}
\subsection{Query-Time Graph Construction}
The pipeline ranks passages before extracting evidence. Structural table
triples associate a row entity with a relation derived from the column header
and a cell value. Where available, hierarchical headers identify the complete
column path. Semantic extraction supplies additional triples from tables and
passages. The graph stores provenance with its edges and resolves entity aliases.
The final paper must document the precise normalization rules and configuration.

\subsection{Planning and Execution}
The planner proposes candidate reasoning paths. A code synthesizer translates
each path into Python that accesses a restricted graph API. Execution records
queried edges and produces either an output or an error. A successful run alone
does not establish that the program implements the question correctly.

\subsection{Evidence-Aware Selection}
The evaluator uses execution outcomes, recorded evidence, source support, and
agreement between candidate outputs. Repeated access to the same source must
not be interpreted as independent corroboration. Edge-access tracing indicates
which evidence was consulted; it does not by itself prove that every arithmetic
operand was derived from that evidence. The exact scoring rule and rejection
conditions must be audited against the implementation before publication.

\subsection{Typed Numerical Programs}
A numerical variant represents lookup and arithmetic operations in a typed
intermediate representation. The experiment will compare it with Python
generation while controlling shared upstream components. Any differences in
fallback behavior must be reported as part of the treatment.

\section{Limitations}
The current experiments assume dataset-supplied tables and, for FinQA, the
associated report context; they therefore do not measure open-domain table or
document retrieval. HiTab is evaluated as hierarchical table-only QA, so it
tests structural and numerical reasoning but cannot demonstrate table--text
provenance diversity. The deterministic table graph preserves row and column
header paths, but graph size grows with the number of cells, while optional LLM
enrichment can introduce redundant parallel edges or noisy relations.

The numerical IR currently covers a practical but incomplete operator set.
Questions involving ranking, ranges, dates, complex percentages, implicit unit
conversion, or domain-specific financial operators may require additional
operators or repair. A successfully executed program is not necessarily a
semantically correct one: it may select the wrong grounded cells, reverse an
ordered subtraction, or apply a valid operator to an incorrect set of values.
Consequently, execution success is reported separately from denotation,
operator, step, and grounding accuracy. Step-level evaluation also depends on
the availability and alignment of gold programs and is not directly comparable
across datasets with different annotation conventions.

Planning and graph enrichment still require multiple model calls, increasing
latency and exposing results to provider failures and model variance. Source
counts are only an approximation of independence because different passages or
edges may repeat the same underlying fact. Full graph traces improve
auditability but can become visually dense and should not be treated as proof
that every extracted edge is correct. Finally, restricted Python execution is
an engineering sandbox rather than a formally verified security boundary.

\section{Conclusion}
This draft defines a study of executable reasoning over query-time table--text
graphs. Final conclusions will depend on controlled benchmark and ablation results.
